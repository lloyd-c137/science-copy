# 审阅工作流

## 1. 确认审阅对象

以固定稿对应的对象及证据快照、学生取舍、答辩和活动要求为准。尚无学生本人的固定提交时说明状态，等正式提交后再形成审阅草稿。

A积累问题，B形成Problem，C比较至少两篇独立来源并发展RQ与解释，D核对价值、方法及关键条件，E准备固定稿与答辩，F本人提交并由老师审阅。理解这一过程用于定位缺口，不按记录数量评分。

## 2. 分项判断

- **价值**：最接近的工作是什么，学生拟增加什么，结果相反或差异很小是否仍有收获？分开学习价值、实际价值、研究贡献。基础档看明确范围内的本人贡献；学生主动表达竞赛目标时再另评竞争力。
- **方法与关键验证**：检查固定提交中的CheckRun是否覆盖相连RQ、hypothesis、method及对应版本，分别审阅rq_alignment、alternative_discrimination、conclusion_limits中的依据：方法能否回答RQ、区分核心解释和替代解释、结论能到什么边界；假设的scope是否受证据支持。结构检查通过不能替代专业判断。根本可行性问题须在开题前用相应材料核实。必要材料、资源或证明基础是否可得？小试解决了哪项疑点，仍有哪些根本问题会改变开题判断？
- **投入与范围**：以活动budget及老师确认例外为准。按当前活动周期核对。分别考虑学习、核查、返工、实践、写作答辩、人力窗口及机器等待，分清实测、自述和估算。
- **本人理解**：从实际预测、解释、核对和取舍找依据，区分AI帮助与学生贡献。说明仍需怎样的材料或一次新例判断，而不是由记录缺失直接推定能力不足。

## 3. 形成可执行草稿

给出可开题、补证后再判或调整方向的建议。判断依据及缺口各用简短文字，优先安排当前最重要的一两项任务。

| 建议 | 必须说清的后续安排 |
| --- | --- |
| 可开题 | 当前周期验收依据；首项正式任务、交付物、完成标准、责任人与日期 |
| 补证后再判 | 具体对象/版本、关键缺口、材料、返回阶段、责任人与复核日期 |
| 调整方向 | 原判断受挑战之处、可保留的兴趣和下一步调整任务 |

字段名和必填条件以`review_save_draft`实际schema为准。版本映射：`project_version`取`project.version`，`requirement_version`取`project.activity.version`，`draft_revision`取`review_draft.draft.revision`（没有草稿时为空字符串），`deliverable_version`取`project.submitted_deliverable`。`object_refs`只引用该固定提交实际包含的对象版本，不混入工作区其他对象。日期优先沿用已有安排，没有安排时可以给出待老师核对的建议。

## 4. 保存并交老师核对

入口、回执和冲突处理见主 Skill「读取、保存与交接」。没有返回链接时，从已读项目的 `return_url` 取链接，旧意见仍跟随原提交版本。
